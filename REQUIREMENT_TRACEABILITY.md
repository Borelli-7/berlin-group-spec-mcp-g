# Requirement traceability

The corpus manifest establishes document identity/version/authority. Curated
requirement mappings establish the engineering association:

```text
Curated requirement ID + mapping-file provenance
                  |
  cited source ID + exact page/semantic locator + evidence hash
                  |
    endpoint path/method + operation provenance
                  |
 source-scoped referenced schemas + schema provenance
                  |
 acceptance criteria from the curated mapping, never generated by an LLM
```

## Mapping format

Register the requirement file as `kind: requirements` in the manifest:

```yaml
requirements:
  - id: OFV2-TRANSACTIONS-001
    version: openfinance-v2
    title: Operator-curated transaction endpoint requirement
    sources:
      - source_id: bg-openfinance-v2-implementation-guidelines
        locator: page:123
      - source_id: bg-openfinance-v2-openapi
        locator: path:/accounts/{accountId}/transactions
    endpoints:
      - path: /accounts/{accountId}/transactions
        method: GET
    acceptance_criteria:
      - "Replace with a reviewed, source-supported acceptance criterion."
    conflicts_with: []
```

This is a format example, not a factual requirement assertion. The included
fixture deliberately uses the `FIXTURE-` ID prefix.

IDs must be unique across the catalog. The mapping version must match the
requirement-file manifest version. Nonempty title, source citations, and
acceptance criteria are required; every source/locator and endpoint must
resolve in the candidate generation before publication. Duplicate citations,
unknown conflict IDs, self-conflicts, and OCR-only citations are rejected.
Cross-version document citations are retained as written, not silently relabeled.

Explicit `endpoints` are preferred and respected. If omitted, endpoint
associations are derived **only** from cited matching-version OpenAPI path or
operation locators, not from searching/guessing PDF prose. A whole-path
citation without explicit endpoints associates all operations on that path;
use `operation:GET:...` or explicit endpoints to restrict it.

## Returned provenance

A `Requirement` has:

* Original/normalized mapping fields (`id`, `version`, `sources`, `endpoints`,
  `acceptance_criteria`, `conflicts_with`).
* Its own `provenance`, pointing to `requirement:ID` in the curated mapping file.
* `resolved_sources`, with the cited source's document ID, version, kind,
  locator, and exact evidence hash.

`trace_requirement` returns the requirement, specification citations,
source-backed endpoint/schema objects, acceptance criteria, and exact related
evidence. The requirement-to-endpoint association is justified by the mapping
provenance; the endpoint-to-schema association is represented by the contract
reference and the referenced schema's provenance. Acceptance criteria inherit
the requirement mapping's provenance, not a fabricated official-document claim.

Keep manifest authority visible during review. A project-curated mapping is
authoritative for the project association, but that does not make its prose an
official normative Berlin Group statement. The included `test` corpus is never
a substitute for official specifications.

## Conflict handling

Declare `conflicts_with: [OTHER-ID]` when a curator has identified contradictory
requirements. Returned conflicts include both mapping and evidence citations.
Structural conflicts also expose different OpenAPI contracts or reachable
schema definitions for the same version/endpoint across sources.

Authority and precedence are returned for human/agent analysis. The service
does not select a winner, merge contradicting contracts, or use natural-language
heuristics to turn "MUST" / "MUST NOT" text into a resolved business decision.
Unrecognized prose conflicts remain the consuming Requirements/Architect
agent's responsibility.

## Agent workflow

The Requirements Agent retrieves a bundle, reads every relevant exact source,
and writes interpreted engineering requirements with citations and mapping IDs.
The Developer Agent implements these while preserving V1 behavior. Requirements
Review verifies source fidelity; Tester uses curated acceptance criteria and
contract differences; Architect Review evaluates the design and compatibility.

The MCP performs none of those interpretations and has no access layer for
application repositories. Version comparison provides concrete evidence for
review, not permission to break backward compatibility.

Retain the snapshot generation with engineering artifacts. After a corpus
update, new document/chunk hashes identify changed evidence. A stable source ID
by itself does not pin a historical document revision.
